\section{Introduction}
\label{sec:intro}

Autonomous coding agents now resolve real repository issues~\cite{jimenez2024swebench,yang2024sweagent,zhang2024autocoderover,xia2024agentless} and run as general software developers~\cite{wang2025openhands}. Teams also run several agents at the same time. Multi-agent frameworks assign roles to agents and make them talk to each other~\cite{qian2024chatdev,hong2023metagpt,wu2023autogen}, and recent reviews list coordination between agents as an open problem in software engineering~\cite{he2025llmmas,hou2024llm4se}. In practice, a developer can start Claude Code in one Git worktree and OpenCode in a second worktree, on the same task or on related tasks. Each agent reads instructions from many sources: the developer prompt, an issue, a rule file such as \texttt{AGENTS.md} or \texttt{CLAUDE.md}, the project documentation, and the repository configuration. These sources often disagree, and the agents do not know which source governs.

The common response is to give agents more memory: layers that store transcripts and extracted facts and return them at the next session~\cite{packer2023memgpt,chhikara2025mem0,rasmussen2025zep,honcho2026}. A memory store keeps an agent's proposal and a maintainer's decision as items of the same kind. Long contexts make this worse: models use the middle of a long context less reliably~\cite{liu2024lost}, their effective context is shorter than the stated window~\cite{hsieh2024ruler}, and irrelevant context lowers accuracy~\cite{shi2023distracted}. When two items conflict, the agent needs a rule that says which item has \emph{standing}, and why.

\paragraph{From Project Truth to effective standing.}
Our first design gave Bridge a central ``Project Truth'' ledger: every agent claim would be reconciled against Git history and test results, and the ledger would be the single source of project state. We rejected this design. A central ledger duplicates systems of record that teams already operate, such as branch protection~\cite{githubbranchprotection}, CODEOWNERS files~\cite{githubcodeowners}, issue assignments, and identity providers~\cite{rfc6749,spiffe2026}. Each duplicate must stay synchronized, and the ledger becomes the bottleneck for every agent action. The replacement thesis is narrower. Bridge does not store authority. It computes \emph{effective standing}: for a given conflict, it derives which directive or change has the authority to decide from the existing records, and it records the evidence. The output is an \emph{effective directive}, not a claim of objective truth.

\paragraph{Contributions.}
This paper makes four contributions:
\begin{enumerate}
    \item A formal model of effective standing (Section~\ref{sec:framework}): a five-state claim lifecycle $\Sset$ (\st{Proposed}, \st{Decided}, \st{Implemented}, \st{Verified}, and \st{Obsolete}), an authority order $\succA$ over directives, and a deterministic resolution operator $\Res$. We relate the model to commitment theory in multi-agent systems~\cite{singh1999commit}.
    \item Two implementations of $\Res$. The first is a directive resolver that ranks instruction sources by tier and recency. The second is \texttt{bridge resolve}, a command that compares two agent worktrees and derives standing from CODEOWNERS at the merge base and from commit signatures.
    \item An evaluation on two benchmarks and one live-agent pilot (Sections~\ref{sec:method} and~\ref{sec:results}). The resolver agrees with 35 of 40 gold statuses on a blind benchmark and never gives a permissive status to a restricted action. The live pilot is incomplete and its pre-registered scorer is defective. We report these defects in full, with a post-hoc trace audit, instead of the scorer's numbers alone.
    \item A failure taxonomy (Section~\ref{sec:analysis}). We define three lifecycle failures (\emph{Ghost Dependency}, \emph{Zombie Constraint}, and \emph{Dead-End Hypothesis Resurrection}) with detection rules, and we separate them from the failures that the pilot data show.
\end{enumerate}

\paragraph{What this paper does not claim.}
We do not claim that Bridge directives improve agent behavior; the pilot cannot support that claim in either direction. We report no results for the work-transfer experiment (EXP-001), whose live pilot was not executed, and Section~\ref{sec:threats} explains why earlier values for it are withdrawn.
